# Orchestrator向け開発依頼

作成日：2026年10月21日


## 1. リポジトリ名候補

`agent-helm` とします。

リポジトリ説明文の案：

> agtxの既存Orchestratorに自然言語で開発を依頼し、Claude・Codexの進捗確認と実行承認を行うWebコンソール。

## 2. 利用方法と事前準備

1. GitHubに `agent-helm` を作成し、Macにクローンする。公開範囲は所有者が決める。
2. 既存の `agtx-playground` とは別プロジェクトとしてagtxを設定する。既存の動作環境を変更しない。
3. 新規リポジトリでagtx TUIと既存Orchestratorを起動する。Claude・Codex・GitHub連携などの前提を確認する。
4. 本書をプロジェクト内に置き、以下の「開発依頼プロンプト」の開始から終了までをOrchestratorに読み込ませる。
5. Orchestratorには調査・設計・タスク作成・実装・レビュー・PR作成まで任せる。必要な実行許可には人間が対応し、PRマージも人間が行う。

読み込み時の指示例：

> `agent-helm-development-prompt.md` の「開発依頼プロンプト」を今回の開発依頼として読み、調査・設計からタスク作成、実装、レビュー、PR作成まで進めてください。PRはマージしないでください。

# 開発依頼プロンプト

ここから下をOrchestratorへの開発依頼とします。

## 1. 目的と成功条件

新規リポジトリ `agent-helm` に、agtxを利用するAI開発チーム向けのWebコンソールを開発してください。

人間が自然言語で開発を依頼すると、既存のagtx Orchestratorが調査、タスク分解・作成、依存関係整理、Codexによる実装、Claudeによるレビュー、PR作成まで進め、人間は進捗確認と必要な承認に集中できることを目指します。

既存の実験では、自然言語による依頼からタスク自動作成、複数エージェントによる実装・レビュー、PR作成、手動マージ後のアプリ動作まで確認されています。一方、ClaudeとCodexの双方でコマンド実行許可が必要でした。

今回のMVPは、**「チャットで指示する・進捗を見る・承認する」** を中心にしてください。Kanbanを人間が頻繁に操作することを前提にしないでください。技術選定の細部は調査後に判断して構いませんが、目的・安全制約・受け入れ条件を守ってください。

## 2. agtxの前提と開始時の調査

### 2.1 既存機能を再利用する

- 既存のagtx Orchestratorを使うA案を採用する。独自Orchestratorを新規実装しない。
- タスク管理、フェーズ遷移、worktree管理、エージェント起動などはagtxに任せる。
- agtx本体の改変やフォークを前提にしない。内部SQLiteへの直接書き込みは禁止し、通常の連携はHTTP API・WebSocket・MCPを利用する。
- 新規のタスク管理DBを作らず、タスク状態の正本はagtxに置く。コンソール固有の設定・送信記録などが必要なら最小限にする。

### 2.2 事前調査で得られた仕様

以下はagtx 1.0.6の調査情報であり、実装前に対象環境で確認してください。

| 項目 | 調査時点の内容・実装への影響 |
|---|---|
| HTTP・WebSocket | `agtx serve` がHTTP API、ペイン配信、内蔵PWAを提供する |
| MCP | `agtx mcp-serve <project>` がタスク操作や状態監視を提供する |
| TUI常駐 | フェーズ遷移はキュー投入後にTUIが実行する。APIの受付成功だけで遷移完了と判断しない |
| 状態の鮮度 | TUI不在では状態が古くなる。`tui_connected`、取得時刻、状態の経過時間を考慮する |
| ボード監視 | ボードが参照されている間に状態更新が行われる仕組みがあり、監視を継続する必要がある |
| タスク操作 | Backlog以外では編集・削除が制限される。許可された操作を確認する |
| Orchestrator | 専用の指示送信APIは確認されていない。タスク向け入力APIと混同しない |
| tmux連携 | 既存Orchestratorへの指示はtmux経由を想定するが、公式APIではなく画面・入力状態に依存する |
| CORS | HTTP APIは同一オリジン前提。ブラウザから直接接続せずBFFで中継する |
| プロジェクトID | 一覧APIのUUIDを利用する。詳細の`project_id`に名前が入る例があり、同一視しない |
| バージョン互換性 | 外部クライアント向けの安定性保証は確認されていない。対応バージョンを記録し契約テストを用意する |

最初に既存の内蔵Web UIを確認し、再利用できる機能と不足している機能を整理してください。実バージョン、起動方法、認証、入力API、イベント形式、Orchestratorペインの特定方法、Claude・Codexそれぞれの承認画面を確認し、調査記録を残してください。調査資料にあるエンドポイント・キー・フィールドを無検証で固定しないでください。

## 3. MVPの機能要件

### 3.1 Orchestratorへの自然言語指示【最優先】

- Web画面から既存Orchestratorへ日本語を含む開発依頼と追加指示を送れること。
- 指示の送信先プロジェクトとOrchestratorを明示すること。
- 指示入力とOrchestratorの画面出力を同じ画面で確認できること。
- A案では応答はペインの画面情報である。完全な会話履歴や構造化されたAI応答が得られるかのように表示しないこと。
- 送信中・送信失敗・結果不明を区別すること。ペインへの送信と、エージェントによる依頼の受理・完了を同一視しないこと。
- 改行、長文、日本語、特殊文字の扱いと入力上限を確認すること。切り詰めた指示を黙って送らないこと。
- 承認画面・補完候補・他の入力と衝突する場合は送信を抑止し、状況を表示すること。Enterの無制限な連打で回避しないこと。

### 3.2 タスクとエージェントの状態表示【最優先】

- タスク名、フェーズ、担当エージェント、実行状態、依存関係、要対応理由を表示すること。
- 実行中、承認待ち候補、レビュー中、フェーズ完了、エラー、切断、状態不明を区別すること。
- `blocked` をすべてコマンド実行許可と決めつけず、理由と画面を確認できること。
- タスク詳細でログまたはペイン出力を確認できること。
- TUI停止、Orchestrator停止、agtxとの切断、古い状態を分かるように表示すること。取得失敗を「タスクなし」や「完了」と扱わないこと。
- ポーリング、MCPのイベント待機、SSE、WebSocketなどから必要最小限の方式を選び、更新頻度と再接続方針を記録すること。

### 3.3 Claude・Codex双方の承認待ちとWeb操作【最優先】

- Claude CodeとCodexの双方が求めるコマンド実行許可に対応すること。Orchestrator自身の承認待ちも確認・操作できること。
- 承認待ちは要対応領域で目立つように表示し、対象プロジェクト・タスク・エージェント・現在の画面・取得時刻を確認できること。
- 構造化された承認情報が取得できるかを調査すること。取得できない場合は最新のペイン表示と明示的なキー入力をMVPの方式としてよい。
- `y`、`n`、数字、Enter、Escape、上下キーなどは実際の選択肢とAPIの対応状況に合わせること。全エージェントで`y=承認`、`n=拒否`とは仮定しないこと。
- 「承認」「拒否」と表示する場合、その画面の選択肢との対応が確認できること。意味を特定できない場合はキー自体を表示し、利用者が画面を見て操作できること。
- 承認操作の直前に対象と画面を再確認すること。画面が変化している、期限切れ、切断、対象が終了した場合は送信せず再確認を促すこと。
- 二重クリックや再接続で同じ入力を再送しないこと。通信結果が不明な場合に変更操作を自動再試行しないこと。
- 送信後はペインや状態を再取得して結果を表示すること。キー送信成功だけで「承認完了」「処理再開」と断定しないこと。
- tmux経由では外部操作との競合を完全には防げない可能性がある。確認と送信の間の競合、検知精度、対応外画面を制約として報告すること。
- 承認は人間が明示的に行う。自動承認、包括的な権限緩和、既存サンドボックスの無効化は実装しないこと。

### 3.4 PRと実装結果の表示【高】

- タスクに関連するPRのURLと状態を、取得可能な情報に基づいて表示すること。
- テスト結果や完了報告を確認できること。構造化データがない場合は出典となるログ・報告を示すこと。
- 未実行・取得不能・不明を成功と表示しないこと。
- PR作成済み、レビュー待ち、手動マージ待ちを区別し、マージ操作は実装しないこと。

### 3.5 PC・スマートフォン対応【高】

- PCとスマートフォンの幅で指示入力、進捗確認、承認操作が使えること。
- 狭い画面でも承認対象と選択肢が隠れず、誤操作しにくい配置にすること。
- MVPではブラウザ内の要対応表示を必須とする。バックグラウンドのWeb Pushや外部通知サービスは必須にしない。
- ローカル起動を基本とし、将来の限定的なリモート利用に対応できる構造とする。スマホ対応のために無断で外部公開しない。

## 4. アーキテクチャとAdapter構成

想定構成は次のとおりです。フレームワークはNext.js / Reactなどを候補に、要件と実装量から選択してください。

```text
PC / スマートフォンのブラウザ
                |
       Web UI + 同一オリジンBFF
                |
       +--------+-------------------+
       |                            |
  AgtxGateway              OrchestratorAdapter
       |                            |
  HTTP / MCP / WS          TmuxOrchestratorAdapter
       |                            |
  agtxのタスク・状態          既存Orchestrator
       |                            |
       +---------- agtx TUI --------+
                       |
                Claude / Codex
```

### 4.1 AgtxGateway

タスク一覧・詳細、状態監視、ペイン読取、タスクへの入力、ヘルス確認をまとめます。たとえば `listTasks`、`getTask`、`waitForChange`、`readPane`、`sendInput`、`getHealth` を境界として設計してください。名称は例示です。

HTTP、MCP、WebSocketの違い、プロジェクトIDの解決、レスポンスの正規化、タイムアウト、エラー、切断処理をこの層に閉じ込めてください。不要なCRUDやフェーズ操作をUIに増やさず、開発の進行は既存Orchestratorに任せてください。

### 4.2 OrchestratorAdapter

Orchestratorの検出、状態取得、画面取得、自然言語指示、必要なキー入力を独立したインターフェースにしてください。MVPは `TmuxOrchestratorAdapter` のみ実装します。

- tmuxソケット、セッション、ウィンドウ、ペインを設定・検証し、`agtx-playground` や固定の番号をハードコードしない。
- 対象が複数で一意に特定できない場合は推測して送らない。
- UIからtmuxやOSコマンドを直接呼び出さない。
- 入力をOSシェルのコマンド文字列に連結しない。プロセス実行は引数を分離し、ユーザーの文章をデータとして扱う。
- 同一ペインへの送信を直列化し、送信中の状態を管理する。
- 停止中や不明な状態で勝手に別のOrchestratorを起動・選択しない。

将来Agent SDK方式などへ差し替えられる境界は用意しますが、B案の実装、SDK認証・課金設定、独自の自律実行ループは今回行いません。

### 4.3 BFFとデータの扱い

BFFはブラウザと同一オリジンでAPIやペイン配信を中継します。接続先やプロジェクトの選択をサーバー側で検証し、任意のURL・ファイル・ペインにアクセスする汎用プロキシにしないでください。状態の正本はagtxとし、UIのキャッシュには取得時刻と切断状態を持たせてください。

## 5. 安全制約

- 初期状態はlocalhostにのみバインドする。agtxのAPIとBFFを無断で全インターフェースへ公開しない。
- 公開トンネル、クラウドへのデプロイ、インターネット公開は行わない。
- リモート接続は将来の運用手順として整理する。限定ネットワーク、HTTPS、認証、アクセス制限を含め、公開設定の実行は別途判断とする。
- localhostでも任意のWebサイトから操作を起動できないよう、Origin/Hostの検証、適切なCSRF対策、WebSocketの接続元検証などを設計する。
- agtxがloopbackで認証不要であっても、その事実をBFFの外部公開時の認証として扱わない。
- ユーザー入力、タスク名、ペイン内容を信頼済みHTMLやシェルコードとして処理しない。ANSI表示なども安全なレンダリングにする。
- APIキー、認証トークン、秘密情報をリポジトリや通常ログに保存しない。画面やログの保存範囲を最小限にし、設定例にはダミー値を使う。
- 破壊的Git操作、PRマージ、mainへの直接コミット、既存環境の削除や再構成は行わない。
- agtxの「Doneへの遷移」等にマージやcleanupが含まれる可能性を確認する。名称だけで安全と判断せず、マージを伴う操作は呼ばない。
- 既存の `agtx-playground` や、この開発を進めているOrchestratorを検証で壊さない。検証用プロジェクト・ペインを分離する。
- テストやビルドにもスクリプト実行が含まれるため、コマンド名だけで権限を自動許可しない。通常の権限制御を維持する。

## 6. 開発手順

1. **調査**：リポジトリの状態、agtxとエージェントのバージョン、既存API・UI、起動・認証方法、承認画面を確認する。調査済み・未確認を区別する。
2. **設計**：技術選定、Adapterの責務、データ取得、画面構成、承認方式、異常時の挙動、テスト方法を簡潔な文書にまとめる。
3. **タスク分解**：agtxのMCPを利用してタスクを自動作成する。各タスクに目的、変更範囲、依存関係、受け入れ条件を記載する。利用可能なら `create_tasks_batch` を活用する。
4. **実装順序の整理**：基盤・Adapter契約を先に定義し、独立したUIや接続処理は並列化する。統合・実機確認を独立した作業として確保する。
5. **実装**：Codexによる実装とClaudeによるレビューを基本に、既存agtxワークフローを使用する。タスクごとに作業ブランチ/worktreeを分け、mainへ直接コミットしない。
6. **レビューと修正**：機能、安全制約、異常系、仕様充足を確認する。問題は修正して再確認する。
7. **統合検証**：PRをmainへマージせず、必要なら一時的な統合ブランチ/worktreeで依存する変更を組み合わせる。単体PRのテストだけで全体を完成扱いしない。
8. **PR作成**：変更内容、確認結果、依存PR、推奨マージ順、未解決事項を記載する。依存関係に応じてベースブランチを設定し、人間が統合できる状態にする。
9. **利用手順の整備**：READMEに前提、対応バージョン、セットアップ、設定例、起動・停止順、承認操作、テスト方法、制約、トラブルシューティングを記載する。
10. **最終報告**：後述の項目を報告し、PRマージ前で停止する。

想定タスクの例は「環境調査・設計」「BFFとAgtxGateway」「TmuxOrchestratorAdapter」「指示・進捗UI」「Claude/Codex承認操作」「PR・結果表示」「スマホ対応」「統合検証・ドキュメント」です。実際の粒度と並列数は調査結果から判断してください。

## 7. 受け入れ条件と検証

以下の各項目を **達成／未達／未検証** で報告し、確認方法と証拠を添えてください。

| ID | 受け入れ条件 | 主な確認方法 |
|---|---|---|
| AC-01 | READMEに従ってローカルで起動し、対象プロジェクトに接続できる | 新しい起動手順で確認 |
| AC-02 | Webから日本語・改行を含む指示を既存Orchestratorへ送り、対応する画面出力を確認できる | 実環境で安全な依頼を送信 |
| AC-03 | agtxのタスク・エージェント状態が更新され、詳細画面を確認できる | 実データとの照合 |
| AC-04 | Claudeの実行許可画面を表示し、画面に合った許可・拒否操作を実施できる | 検証用の無害な操作で確認 |
| AC-05 | Codexの実行許可画面を表示し、画面に合った許可・拒否操作を実施できる | Claudeとは別に確認 |
| AC-06 | Orchestrator自身の承認待ちにも対象を誤らず対応できる | 対象表示と入力先を照合 |
| AC-07 | 古い承認画面、対象終了、二重クリック、通信結果不明で誤送信・自動再送しない | 異常系テスト |
| AC-08 | TUI停止・agtx切断・Orchestrator停止を表示し、完了や空一覧と誤認させない | 個別停止・再接続で確認 |
| AC-09 | 利用可能なPRリンク・テスト結果を表示し、未取得を成功扱いしない | 実例または根拠のある検証データで確認 |
| AC-10 | PCとスマホ幅で依頼・進捗確認・承認操作ができる | 実ブラウザで確認。実端末未確認なら明記 |
| AC-11 | コマンド注入、表示内容のHTML注入、対象外ペインへの操作を防ぐ | 境界値・入力検証テスト |
| AC-12 | 外部公開、PRマージ、mainへの直接コミット、既存環境の破壊を行っていない | 設定と変更・操作履歴を確認 |
| AC-13 | Adapter経由で連携し、agtxの内部DBを書き換えない | コードレビュー |
| AC-14 | 複数PRを組み合わせた状態で、指示・状態表示・承認の一連の流れが動く | 一時的な統合環境で確認 |

プロジェクトに適した型チェック、lint、ビルド、単体・統合テストを実施してください。特にAdapter契約、入力先の検証、承認状態の変化、重複送信、切断・再接続を確認してください。

モックは開発と異常系検証に使用して構いませんが、**モックのテストだけで完了と判断しないでください。** 実ブラウザと実agtxで動作を確認し、Claude・Codex双方の承認フローをそれぞれ検証してください。実環境や権限の都合で確認できない項目は、未検証として再現手順を残してください。一般的な `blocked` の再現だけでは、実行許可への対応を検証したことにはなりません。

また、テストが通っていても仕様を満たしているとは限りません。受け入れ条件と実装・確認結果を照合し、欠落を報告してください。

## 8. スコープ外

今回のMVPでは、以下を原則として実装しません。

- 独自のAI Orchestrator
- 複雑なKanban編集機能
- 複数ユーザー対応
- クラウドへのデプロイ
- GitHub PRの自動マージ
- 自動承認エンジン
- 高度な分析ダッシュボード
- 独自のタスク管理データベース

加えて、Agent SDK方式への移行、完全な構造化会話履歴、バックグラウンドのスマホ通知、公開インターネット向けの運用基盤は今回の完成条件に含めません。将来の改善候補として記録してください。

## 9. 自律実行のルール

- 可能な限り人間の介入なしで進める。
- 実装上の軽微な問題は自律的に解決する。
- 必要なコマンド実行許可は通常の権限制御に従う。
- エラーを無視して成功扱いしない。
